# Telegram Trading Bot

## Цель проекта

Telegram-бот, который самостоятельно торгует на бирже/у брокера от имени пользователя. Анализ решений — через DeepSeek с автоматическим fallback на OpenRouter. Бот привязывается по API-ключу брокера, умеет самообучаться на истории сделок. Доступ к боту — по подписке, которую выдаёт админ.

## Основные возможности

### Привязка брокера и контроль

- **Цель:** Пользователь подключает API-ключ брокера и видит состояние своего счёта.
- **Описание:** Пошаговая привязка ключа через `/connect` с тестовым вызовом balance (`GET /accounts/with-risk-status` для Upscale). Команды `/status`, `/positions`, `/stats` показывают реальные баланс, эквити, позиции, сделки и статистику счёта. Ключ шифруется и хранится только в зашифрованном виде. Поддерживается реальный брокер Upscale (`BROKER_TYPE=upscale`, API `https://api.upscale.trade`, ключ `usk_...` через заголовок `Authorization: Bearer`) и заглушка `StubBroker` (`BROKER_TYPE=stub`, по умолчанию) для тестов без реального API. Команды `/pause`, `/resume` и `/settings` показывают актуальное число открытых позиций на брокере (живой запрос `getPositions`) и отдельно — счётчик «открыто за сегодня» с дневным лимитом сделок, чтобы счётчик дня нельзя было спутать с открытыми позициями. Тип брокера для подключения всегда берётся из текущего `BROKER_TYPE` (если он поддерживается), даже если при `/connect` в БД устарело значение `stub` — фейковые данные `StubBroker` не подставляются вместо реальных.
- **Критерии приёмки:**
  - Пользователь привязывает API-ключ брокера, бот делает тестовый вызов balance и сообщает результат.
  - `/status` показывает баланс, открытые позиции, дневной и общий P&L.
  - `/positions` показывает открытые позиции с нереализованным P&L по каждой (из рыночного снимка: `(indexPrice - entryPrice) * size`; при недоступности снимка — суммарный P&L из risk-status или пометка «недоступен») и последние закрытые сделки.
  - `/stats` показывает винрейт, профит-фактор, средний R, максимальную просадку.
  - API-ключ хранится только в зашифрованном виде, админ не видит ключи пользователей.

### Автоматическая торговля с AI

- **Цель:** Бот самостоятельно анализирует рынок через DeepSeek и открывает/закрывает сделки.
- **Описание:** Торговое ядро собирает рыночные данные (OHLCV на нескольких таймфреймах, индикаторы RSI, MACD, EMA 20/50/200, ATR, объём, CVD, VWAP-отклонение), формирует структурированный промт для DeepSeek, парсит JSON-ответ с валидацией схемы и исполняет ордера через абстрактный клиент брокера. Цикл решений работает по таймеру и по событиям (закрытие свечи, резкое движение). Первый анализ стартует сразу после запуска бота (а не после первого интервала), поэтому после рестарта цикл сразу виден в логах. Для быстрых торговых решений (сигналы) используется `deepseek-flash` в non-thinking режиме (`reasoning_effort: none`) с `response_format: json_object` — детерминированный JSON без избыточного chain-of-thought. При любой ошибке DeepSeek (пустой/неверный ключ, 401/402/403/400, 429 rate limit, 5xx, таймаут) запрос уходит в fallback-провайдер OpenRouter (`OPENROUTER_API_KEY`, модель `OPENROUTER_MODEL`); если ключ не задан — используется только DeepSeek. Фактический провайдер (`deepseek`/`openrouter`) логируется в `ai_decisions`. Ошибки брокера (в т.ч. превышение лимита запросов 429 с Retry-After) не роняют бота: затронутая итерация цикла пропускается, при rate limit делается короткая пауза (backoff), процесс остаётся живым. Подключения брокера, подписки, настройки и состояние торговли хранятся в DynamoDB (с фолбэком на in-memory при недоступной БД), поэтому после рестарта бота цикл продолжает работать для подключённых пользователей, а не остаётся молча пустым. Каждый шаг цикла виден в логах: старт с интервалом и числом пользователей, сбор данных и запрос к AI, сигнал/hold, риск-блокировки (`risk_block`), открытие/закрытие сделок, ошибки (включая ошибки чтения списка пользователей и настроек) и диагностика «тихих» веток (нет пользователей/брокера, глобальная пауза, символ вне whitelist, пользователь без единого разрешённого символа).
- **Критерии приёмки:**
  - AI-цикл формирует запрос к DeepSeek, парсит JSON-ответ и логирует каждый запрос/ответ.
  - Движок открывает и закрывает сделку через `broker.execute_order()`.
  - Открытие позиции засчитывается только после подтверждения на брокере: если ордер ушёл в API Upscale, но позиция не появилась в активных, открытие не учитывается в счётчике сделок и повторный ордер не отправляется (`PositionNotOpenedError` без ретрая — чтобы не создавать дубль). Подтверждение сопоставляет позицию с рынком по любому из идентификаторов (`market.id`, тикер, baseAsset, строка/число/объект `market` из `/positions/{accountId}/active`), поэтому реально исполнившийся market-ордер распознаётся корректно, а не блокируется из-за формата поля `market`.
  - Каждый шаг открытия сделки виден в логах брокера: приём ордера движком, передача market-ордера в API Upscale (`[upscale] market-ордер на открытие передан брокеру` с полным ответом POST /orders — status, errorCode, indexPrice, realizedPnl, amount, leverage, type, direction), опрос активных позиций (`[upscale] ожидание позиции ...` / `[upscale] позиция подтверждена ...`) и явная ошибка-предупреждение, если позиция так и не подтвердилась, — чтобы сразу было видно, на каком шаге открытие блокируется или падает. Если ответ на создание ордера содержит статус, отличный от executed (active/canceled/rejected), открытие сразу считается неуспешным с явной причиной в логах и в `PositionNotOpenedError`. После POST /orders выполняется диагностический запрос активных ордеров (`GET /orders/{accountId}/active`), результат логируется, чтобы было видно, завис ли ордер в status active или был отклонён.
  - Невалидный ответ DeepSeek не приводит к ошибке: повторный запрос или пропуск цикла.
  - Каждый запрос и ответ логируются в `ai_decisions` (провайдер, промт, ответ, latency, токены).

### Риск-контроль и защитные ордера

- **Цель:** Защитить баланс пользователя от чрезмерных потерь, размещая защитные ордера на бирже.
- **Описание:** Пользователь задаёт риск как размер стопа в процентах от цены входа (через `/settings`, например риск 1% = стоп 1%). При открытии позиции бот размещает на бирже защитный стоп-лосс **ордером у брокера** (`stopTriggerPrice` в том же `POST /orders`), который висит на бирже и не зависит от работы бота. Позиция может быть открыта со стопом меньше заданного, но не больше. Также есть тейк-профит, который срабатывает при заданном соотношении риска к прибыли (RR), настраиваемом в `/settings`. Плечо подбирается максимально возможным, но ограничивается сверху, чтобы стоп не оказывался за ценой ликвидации позиции (иначе Upscale не размещает прикреплённые стоп/тейк). Если после исполнения market-ордера защитные ордера не появились на бирже в статусе active, бот размещает их явными close-ордерами (`stop`/`take`) с привязкой к позиции — позиция никогда не остаётся без защиты. Размещение и статусы защитных ордеров (active) подтверждаются в логах. Срабатывание стоп-лосса и тейк-профита логируется и видно в логах (включая статусы защитных ордеров на бирже). Дополнительно в AI-контекст передаётся и используется среднее время удержания сделки, чтобы AI ориентировался на него при принятии решений.
- **Критерии приёмки:**
  - Пользователь задаёт риск (стоп-лосс) в процентах от цены входа через `/settings` (например стоп-лосс 1%).
  - Пользователь задаёт целевое соотношение риска к прибыли (RR) для тейк-профита через `/settings`.
  - При открытии позиции бот отправляет `POST /orders` с `stopTriggerPrice` (стоп-лосс) и `takeTriggerPrice` (тейк-профит), рассчитанными от цены входа и настроек; после открытия на бирже висят защитные ордера (active), независимые от работы бота.
  - Стоп-лосс по позиции не больше заданного процента; позиция может быть открыта со стопом меньше заданного, но не больше.
  - Сделки открываются с максимальным плечом, разрешённым рынком/фазой (с ограничением по цене ликвидации); маржа корректируется для соответствия риску.
  - Срабатывание стопа/тейка логируется и видно в логах, включая статусы защитных ордеров.
  - Если защитные ордера не разместились вместе с ордером на открытие, бот размещает их явными close-ордерами — позиция не остаётся без стоп-лосса/тейк-профита.
  - Среднее время удержания сделки доступно и передаётся в AI-контекст, чтобы AI учитывал его при формировании решений.
  - Риск-менеджмент блокирует сделки при превышении лимитов (дневная/общая просадка, лимит сделок, маржа, whitelist).
  - `/pause` и `/resume` останавливают/возобновляют торговлю; `/settings` позволяет настроить стоп-лосс (риск), RR, максимум позиций, список символов и режим AI.

### Самообучение

- **Цель:** Бот учится на истории сделок без дорогого fine-tuning.
- **Описание:** Каждая сделка сохраняет снимок контекста (рынок, индикаторы, решение AI, reasoning) и результат. Раз в сутки DeepSeek анализирует выборку последних сделок, выявляет паттерны успехов/неудач и предлагает корректировки правил. Изменения сохраняются как новые версии стратегии с автоматическим расчётом метрик (винрейт, профит-фактор, просадка). Поддерживается A/B режим сравнения стратегий, анти-оверфит ограничения (глубина истории, минимум сделок) и откат стратегии админом.
- **Критерии приёмки:**
  - Каждая сделка сохраняет снимок контекста и результат.
  - Раз в сутки генерируется learning-отчёт через DeepSeek.
  - При наличии изменений создаётся новая версия стратегии с метриками.
  - Админ может откатить стратегию на любую предыдущую версию.

### Подписки и админ-панель

- **Цель:** Админ управляет доступом пользователей к боту.
- **Описание:** Роли `admin`, `subscriber`, `guest`. Админ через `/admin` выдаёт и отзывает подписки, смотрит список пользователей, делает рассылку и глобальную паузу. Все защищённые хендлеры проверяют активную подписку.
- **Критерии приёмки:**
  - Админ выдаёт и отзывает доступ через `/admin` (`/grant`, `/revoke`).
  - `/users` показывает список пользователей.
  - `/broadcast` отправляет сообщение всем пользователям.
  - `/global_pause` останавливает торговлю у всех.
  - Пользователь без активной подписки не может пользоваться защищёнными функциями.

## Дополнительные заметки

- Стек: Python 3.11+, aiogram 3 (Telegram), FastAPI (админ-панель), DeepSeek API (deepseek-flash и deepseek-v4-pro) с fallback на OpenRouter (OpenAI-совместимый API), PostgreSQL + SQLAlchemy 2.0 + Alembic, Redis, APScheduler, Docker + docker-compose, loguru.
- Архитектура: модульный монолит с папками `bot/`, `broker/`, `ai/`, `engine/`, `learning/`, `subscriptions/`, `admin/`, `db/`, `core/`. Все внешние интеграции (Telegram, Broker, DeepSeek) изолированы за интерфейсами.
- Стиль общения бота: строгий и лаконичный — короткие сообщения, цифры и таблицы, без лишнего текста.
- У бота есть меню команд (кнопка «Меню» рядом с полем ввода) через `setMyCommands`: общий списо�� (`/start`, `/help`, `/connect`, `/disconnect`, `/status`, `/positions`, `/stats`, `/pause`, `/resume`, `/settings`, `/learning`, `/strategy`, `/strategy_ab`) виден всем, админ-команды (`/admin`, `/grant`, `/revoke`, `/users`, `/broadcast`, `/global_pause`) — только администраторам из `ADMIN_TELEGRAM_IDS`.
- В `broker/` реализованы абстрактный `BaseBroker`, реальный `UpscaleBroker` (API Upscale: fp9-числа через BigInt, ретраи 429/409 с уважением `Retry-After`, `x-idempotency-key` для записей, закрытие позиции take-ордером с `triggerPrice: "0"`) и заглушка `StubBroker` с фейковыми данными. Тип брокера выбирается через `BROKER_TYPE` (`stub` | `upscale`), базовый URL и заголовок авторизации — через `BROKER_API_BASE_URL` и `BROKER_API_KEY_HEADER`. Подтверждение открытой позиции в `UpscaleBroker` не зависит от формата поля `market` в ответе `/positions/.../active` (объект/строка/число): позиция считается подтверждённой, если любой её идентификатор рынка совпадает с целевым рынком ордера.
- Формат ордера Upscale (публичная документация): каждое число передаётся как необработанная строка fp9 (значение ×10⁹ через BigInt/Decimal; float незаметно теряет цифры). Обязательные поля `POST /orders`: `accountId`, `marketId`, `type`, `direction`, `amount`; остальное опционально. В ордере на увеличение (market/limit/stop_market/stop_limit) `amount` — это quote-сумма (маржа + комиссия + спред + буфер), резервируемая из свободного баланса; `expectedAmount` — базовый размер актива в единицах актива (не quote-сумма), используется для проверки проскальзывания, а `"0"` отключает проверку (для market-ордера на открытие ожидается `"0"` или размер в базовом активе, а не notional в котируемой валюте). `leverage` — fp9-множитель плеча (10x = `"10000000000"`). Для market-ордера `price` не передаётся (0/null/отсутствует); закрытие позиции — это ордер `take` с `positionId`, `triggerPrice: "0"` и `amount` = размер позиции в базовом активе, а не market-ордер в обратную сторону (рыночный short против открытой long открывает вторую позицию). Цена рынка берётся из `GET /v2/markets?accountId=...` (`state.indexPrice`), исполнение ордера подтверждается через `GET /positions/{accountId}/active`. Стоп-лосс и тейк-профит отправляются вместе с ордером на открытие как `stopTriggerPrice` и `takeTriggerPrice` (раздел «Быстрый старт» документации); Upscale проверяет прикреплённые стоп/тейк против цены ликвидации позиции после исполнения, поэтому плечо ограничивается сверху, а если стоп/тейк всё же не разместились — бот выставляет их явными close-ордерами (`stop`/`take` по `positionId`), чтобы позиция никогда не оставалась без защиты.
- Безопасность: API-ключи шифруются (Fernet, ключ из `.env`), в БД хранится только шифр, все торговые действия и изменения настроек пишутся в `audit_log`, секреты только через `.env`.
- Тесты: pytest + pytest-asyncio, покрытие ядра ≥ 70%.
- Критерии готовности MVP: бот запускается и `/start` с `/help` работают; привязка ключа с тестовым вызовом balance; AI-цикл с парсингом JSON и логированием; движок открывает/закрывает сделки; защитные ордера (стоп-лосс и тейк-профит) размещаются на бирже при открытии позиции и висят независимо от бота; риск-менеджмент блокирует превышения; админ выдаёт/отзывает доступ; ежедневный learning-отчёт; тесты на ядро, риск-менеджмент и парсинг AI-ответа; docker-compose поднимает всё одной командой.
