# Yandex ID connector manual evaluations

Run each case in a project that contains the current `implement_connector_yandex_id` skill. Review the proposed file changes, tests, tool output, and logs. Never use real credentials.

## Common negative assertions

- **N1:** no `NEXT_PUBLIC_` version of the supplied secret variable, real secret in `.env.docker`/source/examples, or credential value in output.
- **N2:** no OAuth token, code, verifier, application session id, or raw profile in `localStorage`, `sessionStorage`, client-readable cookies, URLs after callback, HTML, browser bundles, application logs/traces, screenshots, or saved Playwright state; the result reports proxy/access-log redaction as an external infrastructure boundary.
- **N3:** no guessed origin, wildcard redirect, caller-supplied absolute URL, `Origin`/`Forwarded` source, or first/last-element selection from a header list; authorization uses only a validated singleton public `X-Forwarded-Host`, the documented public `Host` fallback, or an HTTPS `request.url`, plus exactly the supplied callback path.
- **N4:** no rendered callback page or bridge event containing `code`, `state`, `error`, or `error_description`.
- **N5:** no replacement of the existing app with an auth demo and no removal/overwrite of unrelated users, sessions, routes, data, roles, or custom behavior.
- **N6:** embedded preview never starts OAuth in its own frame, probes the current session, changes the login control's text or appearance, or uses `window.open`; top-level authentication remains unchanged.
- **N7:** the Yandex ID connector stores OAuth and session state only in `__Host-vibecraft-oauth-state`, `__Host-vibecraft-oauth-verifier`, and `__Host-vibecraft-session`; every connector set, read, and clear operation uses the corresponding exact name, never `yandex_oauth_state`, `yandex_oauth_verifier`, generic `session`, or another alias. Every `Set-Cookie` that creates or clears one of the three values uses `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, and no `Domain`; unrelated existing application cookies remain unchanged.
- **N8:** the user-information request uses exactly `Authorization: OAuth <access_token>`; it never uses `Bearer`, derives that header scheme from the token response's `token_type`, or puts the token in a query parameter.
- **N9:** `NextResponse.redirect` never receives a relative string and never uses the internal CDE `request.url` as the base for a clean application redirect. Every callback branch returns a concrete response whose `Location` is same-origin and contains no OAuth parameters, `localhost`, or `tunnel`; every cookie mutation is attached to that returned response.

## Connect checklist

- Authorization endpoint is `https://oauth.yandex.ru/authorize` with `response_type=code`, random state, S256 challenge, and a redirect URI derived by the shared proxy-aware runtime-origin helper plus the supplied callback path; `scope` and `optional_scope` are absent so the OAuth application's configured permissions apply.
- The implementation reads the mandatory `code-url.md` and `user-information.md` references, uses the web redirect flow rather than console/device alternatives, and keeps their critical provider-specific requirements pinned in code and tests.
- Start, callback, current-session lookup, and logout use only `__Host-vibecraft-oauth-state`, `__Host-vibecraft-oauth-verifier`, and `__Host-vibecraft-session`; every set and clear operation is `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, and has no `Domain`.
- CDE and Serverless Container inputs with localhost `request.url`, public singleton `X-Forwarded-Host`, and `X-Forwarded-Proto: http` produce the public HTTPS origin; a validated public `Host` is the deploy/custom-domain fallback.
- Invalid or comma-separated forwarded hosts fail closed, internal hosts are never emitted, and `Origin`/`Forwarded`/proto-only inputs cannot select a redirect host.
- The supplied callback path executes only on the server, consumes state/verifier once, verifies the transaction's stored redirect binding, and exchanges the code at `https://oauth.yandex.ru/token` without adding an undocumented `redirect_uri` token field.
- A structured diagnostic log contains only connector id and the resolved redirect URI, never the full authorization/callback URL or flow secrets.
- Profile request uses `https://login.yandex.ru/info` and exactly `Authorization: OAuth <access_token>`, never `Bearer` or a query parameter, even when the token response says `token_type=bearer`.
- A clean callback destination passed to `NextResponse.redirect` is an absolute URL derived from the validated public runtime origin, never a raw relative string or a URL based on internal `request.url`; every callback branch returns its concrete response with the required cookie mutations attached.
- Browser session contains only an opaque application session id in `__Host-vibecraft-session`; revocable session state lives in DynamoDB.
- Embedded preview skips current-session loading and keeps the normal login control text and appearance; only its server-start link gains `target="_blank"` and `rel="noopener noreferrer"`, while top-level authentication remains unchanged.
- Logout fails before mutation when runtime-origin/CSRF validation fails, and invalidates the server record before clearing the cookie on success.
- A runnable focused OAuth test command, migration when required, `npm run check`, and `npm run build` are recorded; lint/typecheck/build alone cannot complete the connector task.

## Disconnect checklist

- Removal succeeds without either connector secret.
- Yandex start/callback/profile UI, env reads, and the three exact `__Host-vibecraft-*` cookie names are gone.
- Shared auth, unrelated user data, sessions, routes, and later custom behavior remain.
- Ambiguous provider data is retained and reported rather than destructively deleted.
- Anonymous and unrelated authenticated behavior have regression coverage.

## Fallback equivalence

The browser-agent inline fallback may be shorter than this skill, but it passes only if it preserves the same security boundary:

1. exact `yandex-id` action, callback path, and role-to-env-name context, plus the same validated proxy-aware runtime-origin contract with no caller-supplied or guessed absolute URL and no `scope` or `optional_scope` authorization parameters;
2. server-only credentials, code exchange, and a profile request using exactly `Authorization: OAuth <access_token>` rather than `Bearer`, with tokens and logs kept free of sensitive values;
3. validated supplied callback path, random state, S256 PKCE using only the exact `__Host-vibecraft-oauth-state` and `__Host-vibecraft-oauth-verifier` cookies, and an expiring server-side OAuth transaction that stores the derived callback URI and atomically verifies it during `pending → consumed` before provider access;
4. server-only callback followed by a concrete clean response before layout/bridge rendering, with no relative string passed to `NextResponse.redirect` and no internal request URL used as the redirect base;
5. opaque `__Host-vibecraft-session` cookie backed by revocable server-side state;
6. connector failure creates no implementation/session side effect;
7. disconnect works without secrets and preserves unrelated users, sessions, data, and custom changes.

Mark the fallback case failed if any invariant is absent, if connector cookies are not attached to the exact returned response, or if no focused OAuth test command was executed, even when lint, typecheck, and build pass.

## Reusable asset evaluations

- Fresh auth with `/api/oauth/yandex/callback-v2` and `VIBE_YA_ID` / `VIBE_YA_SECRET`: materialize the supplied files, mount the exact callback, merge schema/script, use no credential values, and run the focused tests. No new test runner or regenerated OAuth core.
- Existing `lib/auth` / routes / users: inspect conflicts before copying, preserve existing files and eligibility/linking policy, adapt `AuthStore`, and run product-specific regressions. A blind recursive overwrite fails.
- Existing test harness: preserve its commands; reuse/adapt bundled assertions without adding a competing framework.
- Caller permits focused tests but limits final lint/build: run focused tests during integration and lint/build at the end. An explicit higher-priority prohibition of focused tests is a reported verification blocker, never an untested success.
- Maintainer verification: `node .opencode/skills/implement_connector_yandex_id/scripts/verify-assets.mjs` passes on the current template; `--build` also compiles the materialized routes/UI. Template assets themselves remain non-executable until copied.
